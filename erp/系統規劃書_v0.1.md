# 金鑽保全 智慧勤務系統 規劃書

版本：v0.1（草案）
日期：2026-11-17
狀態：待公司內部討論

---

## 一、為什麼要做這套系統

### 公司規模
| 項目 | 數量 |
|---|---|
| 保全員 | 約 700 人 |
| 案場 | 約 200 個 |
| 排班主管 | 約 14 位，每人負責 6–20 個案場 |
| 每月新進／離職 | 約 30 人 |
| 總公司行政人員 | 6 人 |

### 要解決的三個問題
1. **主管常改班表，會計很難算薪水**
   班表由各主管自行製作，格式不一（Excel、紙本都有）。保全常跨案場、跨主管支援，薪資有月薪、日薪、時薪，主管也可以臨時調整金額。區行政做出時數表和薪資表後，再由會計整合成薪資總表，每一層都靠人工對照。
2. **人事資料一再重複輸入**
   每月約 30 人進出，每人有 18 頁報到文件、勞工名卡等資料，同樣的資料要重複輸入好幾次。
3. **6 位行政人員負擔過重**
   除了人事和薪資，還要負責勞健保、發票、財報、合約、報價、標案、制服設備等業務。

### 系統目標
- **資料只輸入一次**，履歷、名卡、報到文件、薪資都從同一份資料產生。
- **全公司只有一份班表**，每次修改都有紀錄，月底鎖定後直接算薪。
- **會計不必再逐一對照各案場的檔案**，系統直接產出薪資總表。
- **每個案場的損益自動算出來**，讓老闆看得到哪些案場賺錢、哪些不賺。

## 二、現況分析（依日月光案場 114 年 11 月至 115 年 5 月資料）

### 目前流程
```
主管排班（各自的 Excel／紙本）
   ↓
區行政：時數統計表（用人名去數班數 × 12 小時）
   ↓
區行政：案場薪資表（本薪、津貼、加班、扣款、匯款帳號）
   ↓ ＋ 客戶餐廳的餐費結算檔
會計：整合成公司薪資總表 → 匯款
```

### 從檔案中發現的問題
| # | 問題 | 影響 |
|---|---|---|
| 1 | 薪資表有一格公式寫成「兩個減號」，餐費扣款變成加到實領 | 薪資算錯 |
| 2 | 「實際發放總薪資」的加總範圍漏掉一列，和另一個總數相差一人的薪水 | 應付總額錯誤 |
| 3 | 117 筆實領公式有 40 種寫法，59 筆把扣款金額直接寫進公式 | 無法稽核，交接困難 |
| 4 | 留任慰問金依「今天日期」判斷，舊月份重新打開後金額可能改變 | 歷史資料不可靠 |
| 5 | 班表名字打錯一個字，該班就不會被計算 | 少算班數 |
| 6 | 每月統計範圍不同，其中一個月的公式參照到別的月份 | 潛在錯誤 |
| 7 | 加班、歲修時數記在備忘工作表，不會自動計入 | 依賴人工記得 |

> 這些不是個人疏失，而是用 Excel 處理大量薪資時必然會發生的問題。一個案場就有這些狀況，200 個案場的整合工作量和出錯風險可想而知。

## 三、系統範圍

### 這套系統要做的
- 人事報到線上化與文件套印
- 員工主檔、案場主檔
- 排班、出勤確認
- 薪資計算、薪資總表、匯款資料
- 案場損益

### 這套系統不做的（改用現有工具）
| 業務 | 建議工具 |
|---|---|
| 勞健保加退保 | 勞保局、健保署的網路申報系統（系統只提供加退保名單） |
| 電子發票 | 財政部電子發票平台或加值中心 |
| 公司財報、會計帳 | 現有會計軟體或會計師 |
| 簡報、標案文件 | Google 文件／簡報 |

理由：這些業務都有成熟、合法的工具，自己開發反而增加風險和維護成本。

## 四、系統架構

系統分成兩部分：

### A. 人事報到（Google 工具，免費）
```
應徵者填 Google 表單 → Google 試算表 → Apps Script 程式
   → 自動產生履歷表、勞工名卡、報到文件 PDF → 列印、本人簽名
```
- 延續先前討論的規劃，從第一頁履歷表開始，再逐步加入勞工名卡和 18 頁報到文件。
- 錄取後資料自動轉入員工主檔，不必重新輸入。

### B. 勤務薪資系統（自行開發的網頁系統，手機可用）
```
員工主檔、案場主檔
   ↓
主管排班（手機／電腦）→ 異動紀錄
   ↓
月底主管確認出勤 → 區行政檢查 → 關帳鎖定
   ↓
薪資計算 → 薪資總表、匯款檔、案場損益
```

**建議技術**（第三階段開始前再定案）：
- 資料庫：PostgreSQL 雲端資料庫服務（含每日自動備份）
- 網頁：手機與電腦都能使用的網頁，不必安裝 App
- 登入：主管、行政、會計各自有帳號，只看得到自己負責的資料
- 程式碼：存放在公司的 GitHub 專案，任何工程師都能接手

**為什麼不用 Google 試算表做排班薪資？**
每月約 2 萬多個班、14 位主管同時修改，還需要鎖定、異動紀錄和權限控管。試算表在這種規模下會變慢、容易被誤改，也無法控管誰能看哪些薪資資料。

## 五、資料設計（白話說明）

| 資料 | 內容 | 說明 |
|---|---|---|
| **員工** | 員工編號、姓名、身分證、聯絡方式、到職／離職日、銀行帳戶、身分（正職／現金班） | 每人一個固定編號，排班從清單點選，不必打字 |
| **案場** | 案場代號、名稱、客戶、負責主管、區域 | |
| **哨點** | 所屬案場、哨點名稱、等級、班別性質 | 例如日月光的 K1 1哨、K6A 哨 |
| **班別** | 早班、晚班、起訖時間 | 每個案場可自訂 |
| **班** | 哪一天、哪個哨點、哪個班別、誰、實際起訖時間、狀態 | **系統的核心**，薪資從這裡算出來 |
| **異動紀錄** | 誰、什麼時候、改了什麼、原因 | 每次修改班表都自動記錄 |
| **計薪設定** | 某員工在某案場的計薪方式（月薪／日薪／時薪）和金額 | 同一人在不同案場可以有不同設定 |
| **加扣項目** | 有名稱的項目，例如職務津貼、見習費、月訓、借支、制服、眷屬健保、餐費 | 取代「寫在公式裡的數字」 |
| **案場特殊規則** | 例如日月光的留任 A／B／C 分類、慰問金 | 只有特殊案場需要設定 |
| **月結** | 每月關帳的結果與鎖定時間 | 鎖定後的金額永遠不變 |
| **客戶工號對應** | 員工編號 ↔ 客戶給的工號 | 用來自動匯入客戶的餐費檔 |

## 六、各角色的使用方式

| 角色 | 主要工作 |
|---|---|
| **排班主管** | 用手機排班，可複製上個月班表再修改；臨時代班直接改；找現金班人員時也從系統建立；月底確認出勤 |
| **區行政** | 查看負責案場的班表和時數；輸入請假、借支等加扣項；檢查無誤後送出 |
| **會計** | 檢查各區送出的資料；關帳；匯出薪資總表和銀行匯款檔 |
| **人事** | 報到資料審核、員工主檔維護、產生名卡和文件、加退保名單 |
| **老闆／主管階層** | 查看各案場損益、人力成本、異常提醒 |

### 系統自動提醒
- 同一人被排在同一時段的兩個班（跨主管衝突）
- 某個哨點沒有排人
- 工時偏高、連續上班天數過多
- 主管修改金額但沒有填原因
- 關帳期限將至，但還有案場未確認

## 七、薪資計算方式

1. **以「班」為基礎**：每個班依該員工在該案場的計薪設定計算。
   - 月薪：依當月實際班數占應上班數的比例計算
   - 日薪：班數 × 日薪
   - 時薪：實際時數 × 時薪
2. **跨案場**：一個人在多個案場的金額自動合併成一張薪資單，並保留各案場的明細（案場損益會用到）。
3. **主管調整**：主管可以調整某人或某個班的金額，但必須填寫原因，系統會留下紀錄。
4. **加扣項目**：每一筆都有名稱，例如「借支 2,000」，不會只出現一個數字。
5. **勞健保、職福金等扣款**：依投保級距和公司規則計算，規則只寫一次，全公司共用。
6. **關帳鎖定**：月底關帳後，結果固定保存。之後若需更正，以「補發／補扣」方式在下個月處理，並保留紀錄。
7. **與 Excel 並行驗證**：正式上線前，至少有兩個月同時用 Excel 和系統計算，逐一比對差異。

## 八、勞動法規相關原則

- 系統**如實記錄**實際的班和工時，不提供製作第二套班表的功能。
- 工時偏高、連續上班過多時，系統會**提醒，但不會阻止排班**。
- 這些紀錄可以讓公司掌握哪些案場的法規風險最高，以便優先調整。
- 建議諮詢熟悉保全業的勞動法顧問，檢視 84-1 約定和班型設計。
- 薪資計算規則上線前，須由會計、人事確認。

## 九、分階段時程

> 時程為估計值，實際進度取決於資料提供和測試回饋的速度。

| 階段 | 內容 | 預估時間 | 完成標準 |
|---|---|---|---|
| **0 準備** | 申請網域、Google Workspace；收集其他案場、薪資總表、名卡等資料 | 2 週 | 帳號開好、資料到齊 |
| **1 報到線上化** | Google 表單 → 履歷表 PDF → 勞工名卡 → 逐步加入報到文件 | 4–6 週 | 新進人員資料不必再人工輸入 |
| **2 主檔建立** | 員工、案場、哨點主檔；從現有 Excel 匯入 | 4 週 | 700 人、200 案場資料正確 |
| **3 排班試辦** | 排班功能；找 1–2 位主管試用 | 6–8 週 | 試辦主管願意改用系統排班 |
| **4 薪資計算** | 薪資計算、匯出；與 Excel 並行比對兩個月 | 8 週 | 系統結果與人工核對一致 |
| **5 全面推行** | 14 位主管分批導入、教育訓練 | 2–3 個月 | 全公司薪資以系統為準 |
| **6 員工端** | LINE 查班表、補件、通知 | 視需求 | |
| 之後 | 合約、報價單、制服設備管理 | 視需求 | |

第 1、2 階段可以和第 3 階段的設計同時進行。

## 十二、風險與對策

| 風險 | 對策 |
|---|---|
| **主管不願意用** | 手機就能操作、可複製上月班表，要比 Excel 更快；先找願意配合的主管試辦；老闆明確支持 |

| 薪資算錯 | 規則經會計確認、程式測試、與 Excel 並行比對兩個月 |
| 個資外洩 | 公司帳號、權限分級、只開放必要人員、定期檢查分享設定 |
| 系統出問題時沒人能處理 | 程式和文件都存在公司 GitHub；系統掛掉時資料仍可匯出；建議安排外包工程師作為後援 |
| 勞動法規風險 | 如實記錄、系統提醒、諮詢法律顧問 |
